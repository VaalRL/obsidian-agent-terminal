# Agent Terminal Architecture

## 1. Core Modules
- **TerminalManager**: Manages the lifecycle of terminal instances (Creation, Restart, Disposal) and Auto-Sync (`cd` only when the shell itself is in the foreground).
- **PtyService**: Orchestrates the communication between Obsidian and the external `bridge.js` process: over a MessagePort for a utility process (input, resize and queries are queued until the port arrives), or over stdio plus IPC for a child process (readable spawn errors).
- **RuntimeResolver**: Chooses the JavaScript runtime for the bridge: an Electron utility process when Obsidian exposes `remote.utilityProcess` (no Node.js needed), otherwise Obsidian's own Electron with `ELECTRON_RUN_AS_NODE=1` (only where the RunAsNode fuse is still enabled), then system `node` (probed once, cached on success).
- **UtilityProcessHost**: Starts `bridge.js` with `remote.utilityProcess.fork` and hands one end of a `MessageChannelMain` to the bridge and the other to this window; `remote` (synchronous IPC) is only used to set up the connection.
- **bridge / bridgeTransport**: The bridge runs node-pty over one of two transports: a MessagePort (utility process: exits when the port closes, so a reloaded window leaves no process behind; reports the exit code instead of exiting so no output is lost) or stdio plus IPC (child process).
- **NativeInstaller / NativeBundle**: Installs node-pty into `<plugin>/node_modules/node-pty` on first use: asks for consent, downloads the platform bundle from the GitHub release, verifies SHA-256, installs atomically. A manually installed node-pty (no marker file) is left alone.
- **TerminalView**: An Obsidian ItemView that wraps `xterm.js` for UI rendering (header buttons, quick-command menu, clipboard shortcuts). Its xterm theme uses the computed background and text colours of the container (`terminalTheme`), refreshed when the container is shown and on `css-change`, because xterm paints the viewport with `theme.background` and cannot use `transparent`.
- **SettingsTab**: Uses Obsidian's declarative settings API (1.13.1+): `getSettingDefinitions()` describes every setting so Obsidian renders it and indexes it for settings search. Plain controls read and write through `getControlValue` / `setControlValue`, which always save via `plugin.saveSettings()` (re-registering quick-command commands and refreshing open terminals); the shell dropdown is a virtual key backed by `shellPath`, and rows that need custom UI (custom path with folder browser, presets, CLI status, support link) use `render`. Quick commands are a `list` with built-in delete, drag-to-reorder and add; each command is a sub-page (name and command fields, keys `quickCommand:<id>:name|command`) whose entry shows the command and a warning status for permission-skipping flags. Obsidian renders the definitions cached by the last `update()`, so state read by `getControlValue` (such as the detected shells) must not be cleared in `hide()`.
- **QuickCommands / agentTemplates**: Sends a configured command only while the shell is idle (the foreground name is compared with the configured shell, its symlink target and, for macOS `/bin/sh`, the shell it launches; a bridge that does not answer is asked again, then the command is not sent), clearing any half-typed input first; quick commands are also registered as Obsidian commands for hotkeys. Per-agent presets (Claude Code, Antigravity CLI, Codex CLI, opencode) and the detection of permission-skipping flags live here.
- **ObsidianCli**: Detects the official Obsidian CLI (PATH plus the per-platform registration location, Obsidian 1.12.4+) and adds its folder to the terminal's PATH when needed, so agents can control Obsidian.
- **shellEnv**: Strips bridge-only variables (`ELECTRON_RUN_AS_NODE`, the plugin's `NODE_PATH`) from the user's shell environment and declares the terminal's color support (`TERM=xterm-256color`, `COLORTERM=truecolor`, inherited `NO_COLOR` removed — Obsidian started from another tool, e.g. Claude Code, would otherwise pass `NO_COLOR=1` to every CLI).
- **PathResolver**: Calculates the Smart Working Directory (Vault Root, Current File, or Custom Path).
- **EnvironmentService**: Shell detection (presets for the settings dropdown), validation, shell-specific `cd` commands (cmd: `%VAR%` kept literal; WSL: Windows paths translated to `/mnt/<drive>/…`), foreground-shell checks.
- **ContextService**: Analyzes Vault structure and generates dynamic AI instructions/skills (`dataview-expert` only when Dataview is enabled). `performBootstrap()` asks for confirmation through the UI (`ConfirmModal.ask`) when `prepareBootstrap()` reports files that would be replaced, and runs the bootstrap only if confirmed.
- **LinkService**: Writes the AI core (`ai-core.md`, `.ai-core/skills/<name>/SKILL.md`) and links it to the files each agent reads: `CLAUDE.md` (Claude Code, opencode fallback), `GEMINI.md` (Antigravity CLI), `AGENTS.md` (Codex CLI, opencode, Antigravity CLI), … and per-skill links in `.claude/skills` (Claude Code, opencode) and `.agents/skills` (Antigravity CLI, Codex CLI, opencode). Migrates layouts written by older versions (including the pre-rename `intellect.md` / `.intellect`) and backs up user-owned files to `.bak` before replacing them. A SHA-256 fingerprint of the last generated `ai-core.md` (`.ai-core/ai-core.md.sha256`) tells whether it was edited since; edited (or, without a fingerprint, differing) content is copied to `.bak` before the file is overwritten in place. Fallback copies left where linking failed are replaced directly only while they still hold the previous or the new core content; otherwise they are backed up too. On case-insensitive file systems (Windows, macOS) a user-owned file whose name differs from an alias only in case (e.g. `gemini.md` vs `GEMINI.md`) is left untouched and that alias is skipped. Links are relative symlinks on macOS and Linux (absolute ones from earlier versions are replaced), so a moved or synced vault keeps working; on Windows instruction files are hard links and skill folders are junctions, which only accept absolute paths. `prepareBootstrap()` lists, without changing anything, the files a bootstrap would back up (the user's own files, and `ai-core.md` or plugin skills edited since they were generated, detected with `.ai-core/ai-core.md.sha256` and `.ai-core/skill-fingerprints.json`); it shares its decisions (`coreAction`, `isSkillEdited`, `dirNeedsBackup`, `linkAction`) with the bootstrap itself and skips what the legacy migration removes. Symlink targets are computed from real paths, so links inside a folder that is itself a link (e.g. `.claude/skills` pointing outside the vault) resolve correctly.

## 2. Data Flow
1. On load, the plugin writes `bridge.js` (embedded in `main.js` at build time) into its folder.
2. User activates the terminal view; `PathResolver` determines the CWD.
3. `RuntimeResolver` picks a runtime; `NativeInstaller` makes sure node-pty is installed (asking before the first download).
4. `PtyService` starts `bridge.js` with that runtime; the bridge loads `node-pty` from the plugin's `node_modules` and talks to the plugin over a MessagePort (utility process) or stdio plus IPC (child process).
5. `TerminalView` binds the stream to `xterm.js`.
6. When "Bootstrap" is triggered, `LinkService.prepareBootstrap` lists the files that would be replaced; after the user confirms (or when there are none), `LinkService` generates files and creates links for cross-AI compatibility.

## 3. Build & Release
- `esbuild.config.mjs` bundles `bridge.ts` into a string (`virtual:bridge-source`) and, for production builds, embeds `dist/native/native-manifest.json` (`virtual:native-manifest`) — the list of node-pty bundles and their SHA-256.
- `scripts/package-native.mjs` creates `node-pty-<platform>-<arch>.json.gz` (prebuilds for Windows/macOS, locally compiled binary for Linux) and merges bundles produced on different CI machines.
- `.github/workflows/release.yml` builds everything for a version tag and creates a draft GitHub release; the community store installs `main.js` / `manifest.json` / `styles.css`, the plugin downloads the rest.

## 4. Stability & Compatibility
- **Bridge Architecture**: By running `node-pty` in an external process, we bypass Electron's V8 worker restrictions (on Windows node-pty creates a Worker for ConPTY output, which the renderer cannot). Obsidian disables the RunAsNode fuse, so `ELECTRON_RUN_AS_NODE` (and `child_process.fork`) cannot turn Obsidian into Node; a utility process is not affected. node-pty uses N-API, so one binary per platform works with both Electron and Node.js.
- **Hard Link Strategy**: Using Hard Links/Junctions ensures that AI CLI tools recognize instructions as native files.
- **Lifecycle Guard**: Properly kills child processes when the view is closed to prevent memory leaks and zombie processes.
